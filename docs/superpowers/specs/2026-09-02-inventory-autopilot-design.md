# «Автопілот запасів» — дизайн MVP

Дата: 2026-09-02  
Статус: погоджений дизайн перед плануванням реалізації

## 1. Резюме

«Автопілот запасів» — окремий вебзастосунок, який на основі історії покупок прогнозує потреби користувача, підбирає доступні товари в актуальному магазині «Сільпо» та формує персональну чернетку кошика.

Користувач одразу після входу бачить готову чернетку. Для кожної позиції застосунок показує причину рекомендації, рівень упевненості, актуальну ціну, залишок і доступні заміни. Жоден товар не потрапляє до реального кошика без явного підтвердження. Після запису застосунок перечитує кошик через MCP, перевіряє помилки й лише тоді показує checkout-посилання.

Основний режим працює з live MCP «Сільпо». Резервний demo-режим використовує анонімізований snapshot із тією самою внутрішньою схемою даних і завжди явно позначається в UI.

## 2. Цілі MVP

- Показати персональну чернетку одразу після OAuth-входу без обов'язкового onboarding.
- Спрогнозувати потребу на рівні категорії, а потім підібрати конкретний SKU.
- Пояснити кожну рекомендацію фактами з історії покупок.
- Перевірити актуальну наявність, ціну, акції та допустиму кількість.
- Дозволити прибрати, замінити або змінити кількість товару.
- Після явного підтвердження додати вибрані позиції до реального кошика «Сільпо».
- Перевірити фактичний стан кошика й показати checkout-посилання лише за відсутності блокуючих помилок.
- Зібрати трасу MCP-викликів і метрики backtest для демонстрації журі.
- Забезпечити надійний demo fallback без прихованого змішування з live-даними.

## 3. Поза межами MVP

- Обов'язкова анкета вподобань.
- Щотижневі push-, email- або SMS-нагадування.
- Повністю автономне оформлення чи оплата замовлення.
- Автоматичне застосування балабонусів без окремої згоди.
- Fine-tuning, vector database або складна ML-інфраструктура.
- Повний нутриціологічний профіль за відсутності даних у картці товару.
- Нативні мобільні застосунки.
- Multi-agent архітектура.

Налаштування вподобань і плановий щотижневий запуск є наступною ітерацією після MVP.

## 4. Ключові продуктові рішення

### 4.1. Окремий вебзастосунок

Основним інтерфейсом є dashboard, а не чат. Агент працює на бекенді й проявляється через готову чернетку, пояснення, заміни та контрольований запис у кошик.

Чат у майбутньому може підтримувати команди на кшталт «вкладися у 1 000 грн» або «запропонуй менш калорійні снеки», але не є основною навігацією MVP.

### 4.2. Категорія → SKU

Модель не намагається напряму вгадати кожен точний SKU. Спочатку детермінований prediction engine оцінює повторювану потребу: вода, напої, снеки, готова їжа тощо. Потім resolver:

1. шукає звичний SKU за точним артикулом;
2. перевіряє актуальну доступність;
3. за потреби знаходить схожий товар або заміну;
4. порівнює ціну, акції та доступні харчові атрибути;
5. передає Gemini тільки перевірених кандидатів.

### 4.3. Human-in-the-loop

Чернетка є read-only пропозицією. Write-виклик до кошика дозволений лише після окремої дії користувача «Додати у кошик “Сільпо”».

## 5. Технічний стек

### Вебзастосунок

- Next.js App Router і TypeScript.
- React Server Components для початкового завантаження.
- Route Handlers для OAuth callback, синхронізації, генерації чернетки й підтвердження кошика.
- Postgres для сесій, нормалізованої історії, прогнозів, чернеток і трас.
- Drizzle ORM для схеми й запитів.
- Zod для runtime-валідації на всіх зовнішніх межах.
- Vercel як цільовий deployment.

### Агент

- Vercel AI SDK Core.
- Google Generative AI provider: `@ai-sdk/google`.
- Модель: `gemini-3.7-flash`.
- Google AI Studio / Gemini Developer API.
- `@ai-sdk/mcp` та офіційний MCP TypeScript SDK для Streamable HTTP і OAuth.
- `thinking: low` за замовчуванням; `medium` лише для неоднозначного вибору замін.
- Низька випадковість і Zod-валідовані structured outputs.

Секрети:

- `GOOGLE_GENERATIVE_AI_API_KEY` існує лише на сервері.
- `AGENT_MODEL=gemini-3.7-flash` дозволяє змінити модель без редагування коду.
- MCP access/refresh tokens зберігаються зашифрованими й ніколи не потрапляють у client bundle.

### 6.1. Межі модулів

#### `SilpoGateway`

Єдиний внутрішній інтерфейс до даних «Сільпо». Live- і demo-адаптери повертають однакові типи. Решта застосунку не знає, звідки отримані дані.

Відповідальність:

- OAuth-aware MCP connection;
- `tools/list` на початку live-сесії;
- виклики обраного підмноження tools;
- Zod-валідація `structuredContent`;
- нормалізація технічних помилок;
- структурований trace без секретів.

#### `PurchaseNormalizer`

Перетворює офлайн-чеки й онлайн-замовлення у спільну модель:

- дедуплікує онлайн-замовлення та відповідний фіскальний чек;
- виключає пакети, доставку, доплату за прискорення й службові рядки;
- нормалізує одиниці, кількість, назви та артикул;
- фіксує місто й тип каналу;
- групує SKU в категорії потреб;
- позначає ситуативні та потенційно регулярні покупки.

#### `PredictionEngine`

Чиста TypeScript-бібліотека без залежності від React, MCP або Gemini. Приймає нормалізовані покупки та повертає кандидатів категорій із числовими ознаками й confidence.

#### `ProductResolver`

Перетворює прогноз категорії на актуальний товар:

- надає перевагу відомому `externalProductId`;
- шукає точний артикул через batch search;
- перевіряє `available`, `stock`, `step`, `displayRatio`, ціну й special prices;
- знаходить схожі продукти або replacements;
- за необхідності завантажує product details;
- не повертає недоступний товар як підтверджуваний кандидат.

#### `DraftAgent`

Gemini отримує мінімальний нормалізований контекст, список потреб і дозволених товарів. Модель:

- формулює коротке пояснення;
- ранжує лише надані альтернативи;
- позначає відсутні харчові дані;
- повертає строго типізовану чернетку.

Модель не обчислює залишки, не створює товарні ID і не виконує write-операції.

#### `CartCommitService`

Детермінований серверний сервіс, який виконує підтверджений запис, забезпечує ідемпотентність і перевіряє фінальний кошик.

## 7. Агентний workflow

```text
SYNC_HISTORY
  → NORMALIZE
  → INFER_NEEDS
  → RESOLVE_SKUS
  → ENRICH
  → CREATE_DRAFT
  → WAIT_FOR_APPROVAL
  → COMMIT_CART
  → VERIFY_CART
```

### 7.1. High-level tools агента

Gemini не отримує всі 40 raw MCP tools. На кожному етапі доступно не більше п'яти вузьких інструментів:

- `load_customer_context`
- `load_purchase_history`
- `find_available_products`
- `compare_product_alternatives`
- `propose_cart_draft`

`commit_confirmed_cart` не є загальнодоступним інструментом агента. Його викликає Route Handler лише за наявності серверного запису підтвердження користувача.

### 7.2. Обмеження циклу

- максимум шість модельних кроків для створення чернетки;
- timeout на повну генерацію;
- окремий timeout на MCP-виклик;
- завершення одразу після валідного structured output;
- жодних автоматичних повторів write-виклику без перевірки idempotency record;
- model output не є джерелом істини для ціни, stock або ID.

## 8. Prediction engine v1

### 8.1. Кандидати

- вікно історії: до 180 днів;
- exact-SKU кандидат потребує щонайменше двох спостережень;
- category-кандидат потребує щонайменше трьох спостережень;
- покупки в поточному місті мають повну вагу;
- покупки в інших містах мають вагу 0,35;
- службові рядки не враховуються;
- кілька чеків у межах короткої поїздки можуть бути об'єднані в одну ситуативну сесію.

### 8.2. Ознаки

- weighted purchase count;
- медіанний інтервал між покупками;
- median absolute deviation інтервалів;
- час від останньої покупки;
- типова кількість;
- частка покупок у поточному місті;
- повторюваність категорії;
- наявність точного звичного SKU.

### 8.3. Confidence

Початкова евристика:

```text
confidence =
  0.40 × due_score
+ 0.35 × repeat_score
+ 0.25 × stability_score
```

Усі складові нормалізовані в діапазоні 0–1. Ваги зберігаються як конфігурація та змінюються лише після rolling backtest.

- `confidence < 0.55`: abstain;
- `0.55–0.74`: середня впевненість;
- `≥ 0.75`: висока впевненість.

Категоріальний прогноз визначає потребу. Exact-SKU history впливає на вибір товару, але не може самостійно створити високу впевненість за нестабільного циклу.

## 9. MCP-потоки

### 9.1. Початок live-сесії

1. `tools/list`
2. `silpo_get_my_shopping_cart`
3. якщо кошик існує: `silpo_get_shopping_cart_by_id`
4. негайно: `silpo_get_time_slots`
5. якщо слот невалідний, користувач обирає новий до cart-залежних операцій

Якщо кошика немає, створення проходить через address → delivery types → branch → time slots → create cart → cart verification.

### 9.2. Контекст і історія

- `silpo_get_my_family`
- `silpo_get_my_food_restrictions`
- `silpo_get_loyalty_info`
- `silpo_get_my_online_orders`
- `silpo_get_my_offline_orders`

Повне ім'я, телефон, email, точна адреса й номер картки не передаються Gemini.

### 9.3. Формування чернетки

- `silpo_find_products_batch`, переважно за `externalProductId`;
- `silpo_get_promotions`;
- `silpo_get_product_details` для обмеженого набору кандидатів;
- `silpo_get_similar_products` або `silpo_get_replacements`.

### 9.4. Підтвердження кошика

1. прийняти унікальний idempotency key від підтвердженої чернетки;
2. перевірити `cart_commits`: для завершеного key повернути збережений результат, не виконуючи новий write;
3. перечитати кошик;
4. негайно перевірити слот;
5. повторно знайти підтверджені SKU й перевірити stock;
6. один раз обчислити абсолютну цільову кількість: поточна кількість + підтверджена добавка;
7. до write зберегти idempotency key, абсолютні цільові кількості й статус `pending`;
8. викликати `silpo_add_or_update_cart_products` з `addQuantity=false`;
9. негайно перечитати кошик;
10. зберегти verified або blocked result і показати всі error/warning validations;
11. повернути checkout links лише за відсутності блокуючих помилок.

Після невизначеного мережевого результату retry використовує вже збережені абсолютні цільові кількості, а не обчислює їх повторно з оновленого кошика. Тому повтор тієї самої підтвердженої операції не збільшує кількість двічі.

## 10. Дані

### Основні таблиці

- `users`: внутрішній ID і мінімальні налаштування;
- `mcp_connections`: зашифровані токени, expiry, scope;
- `purchase_receipts`: канал, дата, місто, суми, зовнішній fingerprint;
- `purchase_items`: receipt, external product ID, category, quantity, price;
- `product_snapshots`: product ID, external ID, branch, ціна, stock, attributes, captured_at;
- `prediction_runs`: версія алгоритму, часовий cutoff, метрики й статус;
- `predicted_needs`: category, features, confidence, reason codes;
- `drafts`: user, source run, mode, status, total;
- `draft_items`: resolved product, quantity, price snapshot, reason, user decision;
- `cart_commits`: idempotency key, confirmation timestamp, target quantities, result;
- `tool_traces`: tool name, duration, sanitized status, correlation ID.

Raw MCP response не зберігається без потреби. Snapshot для demo анонімізується й не містить токенів, телефонів, адрес або loyalty identifiers.

## 12. Помилки, довіра й безпека

- Кожна рекомендація має confidence і reason codes.
- Агент використовує abstain замість непідтвердженого припущення.
- Недоступний товар не додається; UI пропонує заміну або видалення.
- Невідомий склад чи харчова цінність показується як «даних недостатньо».
- За `401` сервер намагається оновити токен, потім просить повторний вхід.
- За `429` застосовується обмежений exponential backoff.
- Live-режим не перемикається на demo автоматично.
- Зміна ціни чи stock між draft і confirm показується користувачу перед записом.
- Кількість ніколи не перевищує stock і відповідає `step`.
- Пакети і службові позиції ігноруються.
- Балабонуси застосовуються тільки після окремої згоди.
- Checkout не показується як готовий за наявності error validation.
- Логи не містять токенів або персональних ідентифікаторів.

## 13. Тестування

### Unit

- дедуплікація онлайн-замовлення та чека;
- фільтрація службових позицій;
- нормалізація категорій і одиниць;
- median intervals і confidence;
- location weighting;
- abstain;
- відсутність time leakage;
- абсолютні cart quantities та idempotency.

### Contract

Zod fixtures для:

- відсутнього кошика;
- простроченого слота;
- нульового stock;
- зміни ціни;
- часткової доступності;
- `401`, `429`, malformed response;
- error/warning validations.

### Integration

Demo adapter проганяє:

```text
sign in → history → prediction → draft
→ edit → confirm → cart commit → verify → checkout
```

### End-to-end гарантії

- до підтвердження немає write-викликів;
- retry не дублює кількість;
- unavailable item не додається;
- checkout відсутній при error validation;
- demo mode явно позначений;
- partial failure відображається per item.

### Live smoke

- read-only smoke запускається регулярно;
- write smoke запускається вручну;
- кожен write завершується перевіркою кошика;
- trace доступний для демонстрації.

## 14. Валідація прогнозу

Rolling backtest використовує лише покупки до прогнозованої дати.

Метрики:

- exact-SKU `precision@K`;
- exact-SKU `recall@K`;
- `category precision@3`;
- hit rate чеків;
- coverage;
- confidence calibration;
- acceptance rate;
- replacement rate;
- фактична економія прийнятих замін.

Baseline: найчастіші товари за попередні 90 днів.

Поточна контрольна точка на доступній історії:

- 30 офлайн-чеків;
- 81 унікальний SKU;
- 12 повторних SKU;
- exact-SKU precision простого cycle baseline: 2,1%;
- category precision@3 демонстраційного baseline: 42,4%;
- category recall@3: 60,9%.

Ці числа є стартовим результатом, а не продуктовою обіцянкою.

## 15. Нефункціональні критерії

- Demo draft має цільовий p95 не більше 2 секунд від запиту до стану `ready`.
- Live draft має цільову медіану не більше 12 секунд без урахування інтерактивного OAuth і backoff після зовнішнього rate limit; p95 вимірюється, але для MVP не є release gate.
- Усі зовнішні дані проходять runtime-валідацію.
- Зміна model provider не потребує зміни prediction engine або UI.
- Live- і demo-адаптери проходять один contract test suite.
- Кожен prediction run має algorithm version і temporal cutoff.
- Кожен cart commit має idempotency key і verified result.

## 16. Критерії готовності MVP

MVP готовий, коли:

1. користувач проходить OAuth і бачить персональну чернетку;
2. чернетка пояснює кожну позицію та показує confidence;
3. товари мають актуальну ціну, stock і доступні заміни;
4. користувач редагує й явно підтверджує вибір;
5. підтверджені товари ідемпотентно додаються в реальний кошик;
6. фінальний кошик перечитується й validations відображаються;
7. за валідного кошика показуються checkout links;
8. той самий сценарій працює на позначеному demo snapshot;
9. rolling backtest і MCP trace доступні на demo-екрані;
10. автоматизовані unit, contract та end-to-end тести проходять.

## 17. Майбутні ітерації

1. Налаштування вподобань після першої автоматичної чернетки.
2. Щотижневий cron і нагадування.
3. Персональний бюджет та оптимізація суми кошика.
4. Розширений нутриціологічний профіль.
5. Навчання confidence weights на feedback користувачів.
6. Другорядний conversational interface.
