# Tasks 1–2 Project Foundation Design

Status: approved design for implementation planning on 2026-09-02

## 1. Purpose

Tasks 1 and 2 establish the executable and semantic foundation for the «Автопілот запасів» MVP. Task 1 creates a reproducible Next.js application and evidence-producing test harness. Task 2 freezes the shared domain language, the `SilpoGateway` port, typed application results, and the only supported server-environment access path.

This specification narrows and clarifies Tasks 1 and 2 in [`docs/tasks.md`](../../tasks.md). It does not replace the product, architecture, agent, or design-system documents. Where this document is silent, those normative documents continue to apply.

## 2. Goals

- Make a fresh checkout installable and verifiable with `pnpm`.
- Provide one minimal App Router page that proves React rendering, global CSS, and Ukrainian document metadata work.
- Provide fast unit/component tests with Vitest, jsdom, and Testing Library.
- Reserve Playwright as the repository-wide browser and responsive test runner.
- Define stable domain types and runtime schemas before live, demo, persistence, prediction, or UI modules depend on them.
- Make live and demo Silpo adapters interchangeable through one `SilpoGateway` contract.
- Enforce server configuration once, without exporting `process.env` or secret-bearing objects to client code.
- Turn safety-sensitive cart and checkout invariants into types and schemas where Task 2 can enforce them.

## 3. Non-goals

- No OAuth, MCP, Gemini, database, prediction, cart-write, or dashboard implementation.
- No demo fixtures or live integration calls.
- No production dependency beyond the Task 1 package list.
- No full visual dashboard. Task 1 provides only the CSS entry point, base page canvas, and system typography; Task 14 remains responsible for dashboard components and the complete brand-token implementation.
- No persistence models or repository interfaces.
- No model-output schema. The `Draft` domain schema is not the Gemini `DraftProposalSchema` defined by the agent architecture.
- No `.env.example`; Task 18 owns that file.

## 4. Governing decisions

### 4.1. One foundation, two commit boundaries

The work is planned as two sequential implementation tasks. Task 1 must be green before Task 2 begins. Each task has its own red-green-refactor cycle, review gate, and commit. The shared-contract commit is the freeze point described by `AGENTS.md`; later contract changes require controller approval and dependent-task impact review.

### 4.2. Package and module conventions

- `pnpm` is the only package manager.
- The repository is one private workspace package, not a monorepo of deployables.
- TypeScript runs in strict mode and uses the `@/*` alias for `src/*`.
- Application code uses ESM syntax.
- File names use lowercase kebab-case except framework-mandated names.
- No module reads `process.env` except `src/lib/env.ts`.

### 4.3. Environment ambiguity resolution

Task 2's backlog example imports `parseServerEnv`, while the same task says that only `getServerEnv()` may be exported. The approved resolution is:

```ts
export function getServerEnv(source: NodeJS.ProcessEnv = process.env): ServerEnv;
```

`getServerEnv` is the sole public parser and reader. The optional source is a deterministic test seam; production callers pass no argument. There is no exported `parseServerEnv`, no exported raw schema, and no exported `process.env` reference.

The architecture lists `PUBLIC_BASE_URL` as required even though the Task 2 checklist abbreviates the required-key list. The higher-precedence architecture requirement applies: `PUBLIC_BASE_URL` is validated in Task 2.

### 4.4. Domain schemas and TypeScript types

Runtime schemas are the source of truth for serializable domain objects. Their TypeScript types are inferred with `z.infer` wherever practical. Port-only inputs that contain no external data may remain interfaces, but their constituent values use the validated domain types.

Schemas reject unknown keys with `.strict()` at external boundaries. Numeric values must be finite. IDs are non-empty strings. Monetary values are non-negative numbers expressed in hryvnia as documented by the normalized Silpo boundary; this task does not introduce a second minor-unit representation.

### 5.2. Package contract

`package.json` is private and exposes exactly these standard commands:

```json
{
  "scripts": {
    "dev": "next dev",
    "build": "next build",
    "lint": "eslint .",
    "typecheck": "tsc --noEmit",
    "test": "vitest run",
    "test:watch": "vitest",
    "test:e2e": "playwright test"
  }
}
```

Runtime dependencies are `next`, `react`, `react-dom`, and `zod`. Development dependencies are `typescript`, Node/React type packages, `eslint`, `eslint-config-next`, `tailwindcss`, `@tailwindcss/postcss`, `postcss`, `vitest`, `jsdom`, `@vitejs/plugin-react`, Testing Library DOM/React/jest-dom packages, and Playwright Test. The lockfile records the concrete compatible versions selected at implementation time.

Task 1 must not install Drizzle, AI SDK, MCP, database, or UI-component packages owned by later tasks.

`.gitignore` excludes `node_modules`, `.next`, `out`, coverage, Playwright reports/results, local `.env*` files, TypeScript build metadata, `next-env.d.ts`, and pnpm debug logs. It explicitly allows the synthetic `.env.example` owned by Task 18.

### 5.3. TypeScript and lint contract

- `strict` is enabled.
- `noEmit` is enabled for the typecheck path.
- `moduleResolution` is compatible with the current Next.js App Router toolchain.
- `jsx` uses the JSX runtime selected by the installed Next.js toolchain. For Next.js 16.3.4 this is `react-jsx`; if a future supported Next.js release rewrites the setting, commit the generated value and update this specification in the same change.
- `@/*` resolves to `./src/*`.
- Next-generated TypeScript plugin settings and `.next/types/**/*.ts` include paths are retained.
- ESLint checks JavaScript, TypeScript, and TSX source through the Next.js Core Web Vitals and TypeScript presets.
- Generated `.next` output and other standard build artifacts are ignored by lint.

### 5.4. Test-harness contract

Vitest:

- runs in `jsdom`;
- loads `vitest.setup.ts` before tests;
- resolves `@` to `src` exactly as TypeScript does;
- transforms TSX with the React plugin;
- exposes Vitest globals or imports them consistently across the repository;
- restores mocks between tests.

Testing Library:

- extends assertions with `@testing-library/jest-dom/vitest`;
- tests public roles, names, and visible behavior rather than private DOM structure.

Playwright:

- discovers tests under `tests/e2e`;
- uses `http://127.0.0.1:3000` as its default base URL;
- starts `pnpm dev` when no reusable local server is available;
- keeps browser execution out of the Task 1 required verification because no E2E test exists yet.

### 5.5. Landing-page behavior

- The root document language is `uk`.
- Metadata title is `Автопілот запасів`.
- `/` renders one `<main>` landmark and one level-one heading named `Автопілот запасів`.
- The page must render without an environment file, database, network call, or client-side JavaScript hook.
- Global CSS uses the system-first font stack from the design system and a neutral canvas. It does not copy Silpo assets or implement the later dashboard.

### 5.6. Task 1 acceptance scenarios

1. Rendering `HomePage` in jsdom exposes a visible heading named `Автопілот запасів`.
2. `pnpm test` discovers and passes the landing-page test from a fresh invocation.
3. `pnpm lint` exits zero without suppressing relevant Next.js or TypeScript rules.
4. `pnpm typecheck` exits zero under strict TypeScript.
5. `pnpm build` creates a production Next.js build without requiring server secrets.
6. The resulting scripts are the standard commands later tasks can rely on unchanged.

## 6. Task 2 — Shared domain contracts

### 6.1. Contract ownership

`src/features/shared/contracts.ts` is the only Task 2 domain-contract file. It may import Zod, but it must not import React, Next.js, MCP SDK, AI SDK, a database client, or `src/lib/env.ts`. The file defines serializable facts and ports, not provider behavior.

The implementation may group schemas by domain section within the file. It must not split the shared contract across new unowned files during Task 2.

### 6.2. Shared primitives

The module exports these validated primitives and inferred types:

```ts
DataModeSchema          // "live" | "demo"
PurchaseChannelSchema   // "offline" | "online"
ConfidenceBandSchema    // "medium" | "high"
NutritionStatusSchema   // "known" | "insufficient"
DraftStatusSchema       // syncing | generating | ready | confirming |
                        // partially_committed | verified | blocked
ValidationSeveritySchema // "warning" | "error"
```

Confidence is constrained to `0..1`. Task 2 represents only emitted candidates, so `NeedCandidate.confidenceBand` has no `low` value: scores below `0.55` abstain before a candidate is created.

### 6.3. Purchase contracts

```ts
interface RawPurchaseItem {
  sourceId: string;
  externalProductId: number | null;
  productId: string | null;
  name: string;
  quantity: number;
  unit: string | null;
  unitPrice: number;
}

interface RawPurchaseReceipt {
  sourceId: string;
  channel: "offline" | "online";
  purchasedAt: string;
  city: string | null;
  total: number;
  items: RawPurchaseItem[];
}

interface NormalizedPurchaseItem {
  sourceId: string;
  externalProductId: number | null;
  productId: string | null;
  name: string;
  normalizedName: string;
  categoryKey: string;
  quantity: number;
  unit: string | null;
  unitPrice: number;
}

interface NormalizedReceipt {
  sourceIds: string[];
  channel: "offline" | "online";
  purchasedAt: string;
  city: string | null;
  total: number;
  externalFingerprint: string;
  items: NormalizedPurchaseItem[];
}
```

Validation rules:

- source IDs, names, normalized names, categories, and fingerprints are non-empty;
- external product IDs are non-negative integers when present;
- `purchasedAt` is an ISO-8601 datetime;
- quantity is positive and finite;
- unit price and receipt total are non-negative and finite;
- receipts contain at least one item after normalization;
- `sourceIds` is non-empty and contains unique values.

### 6.4. Prediction contracts

```ts
interface NeedFeatures {
  weightedPurchaseCount: number;
  medianIntervalDays: number;
  intervalMadDays: number;
  daysSinceLastPurchase: number;
  activeCityShare: number;
  repeatScore: number;
  dueScore: number;
  stabilityScore: number;
}

interface NeedCandidate {
  categoryKey: string;
  confidence: number;
  confidenceBand: "medium" | "high";
  typicalQuantity: number;
  reasonCodes: string[];
  preferredExternalProductIds: number[];
  features: NeedFeatures;
}
```

Feature scores and shares are constrained to `0..1`; counts and durations are non-negative and finite. `typicalQuantity` is positive. Reason codes are non-empty, unique strings. Preferred external product IDs are unique non-negative integers. Candidate confidence must agree with its band: `0.55 <= medium < 0.75` and `high >= 0.75`.

### 6.5. Product and resolution contracts

```ts
interface Promotion {
  id: string;
  label: string;
  price: number | null;
}

interface NutritionFacts {
  caloriesKcal: number | null;
  proteinGrams: number | null;
  fatGrams: number | null;
  carbohydrateGrams: number | null;
}

interface ProductCandidate {
  productId: string;
  externalProductId: number;
  slug: string;
  name: string;
  imageUrl: string | null;
  price: number;
  specialPrice: number | null;
  available: boolean;
  stock: number;
  step: number;
  displayRatio: number;
  nutritionStatus: "known" | "insufficient";
  nutrition: NutritionFacts | null;
  promotions: Promotion[];
}

interface ProductSearchResult {
  query: string;
  products: ProductCandidate[];
}

interface ProductDetails extends ProductCandidate {
  description: string | null;
  ingredients: string | null;
}

interface ResolvedNeed {
  need: NeedCandidate;
  selected: ProductCandidate;
  alternatives: ProductCandidate[];
}
```

Prices, stock, steps, display ratios, and known nutrition numbers are non-negative and finite; `step` and `displayRatio` are greater than zero. A `specialPrice`, when present, cannot exceed the regular price. `nutrition` is required when status is `known` and must be `null` when status is `insufficient`. Selected and alternative product IDs are unique within one resolved need. An unavailable or zero-stock product may be represented for explanation or replacement handling, but later services must not treat it as confirmable.

### 6.6. Customer, slot, and cart-context contracts

```ts
interface CustomerContext {
  familySize: number | null;
  restrictionKeys: string[];
  loyaltyBonusAvailable: number | null;
}

interface TimeSlot {
  id: string;
  startsAt: string;
  endsAt: string;
  available: boolean;
}

interface CartContext {
  cartId: string;
  deliveryType: "delivery" | "pickup";
  city: string | null;
  branchId: string | null;
  slot: TimeSlot;
}

type CartContextResult =
  | { status: "ready"; context: CartContext }
  | { status: "needs_slot"; availableSlots: TimeSlot[] };

interface UpdateCartContextInput {
  deliveryType: "delivery" | "pickup";
  addressId: string | null;
  branchId: string | null;
  slotId: string;
}
```

`CustomerContext` is already sanitized: it contains no name, phone, email, address, barcode, profile ID, or token. Family size is a positive integer when known. Restriction keys are unique. Loyalty bonus is informational and non-negative. A ready cart context always contains an available slot whose end is after its start.

`addressId` is allowed only in the gateway input needed to establish cart context. It is not part of model input, `Draft`, logs, or client-facing diagnostics.

### 6.7. Draft contracts

```ts
interface DraftItem {
  productId: string;
  externalProductId: number;
  name: string;
  quantity: number;
  price: number;
  stock: number;
  step: number;
  confidence: number;
  confidenceBand: "medium" | "high";
  reasonCodes: string[];
  reason: string;
  nutritionStatus: "known" | "insufficient";
  alternatives: ProductCandidate[];
}

interface Draft {
  id: string;
  mode: "live" | "demo";
  status: DraftStatus;
  algorithmVersion: string;
  trainingCutoff: string;
  summary: string;
  items: DraftItem[];
  total: number;
  version: number;
}
```

Draft requirements:

- IDs and `algorithmVersion` are non-empty.
- `trainingCutoff` is an ISO-8601 datetime.
- summary length is at most 180 characters.
- item reason length is at most 160 characters.
- product IDs are non-empty and unique within a draft.
- quantities are positive, finite, do not exceed stock, and are exact multiples of `step` within numeric tolerance.
- prices and totals are non-negative and finite.
- confidence and confidence band obey the same thresholds as `NeedCandidate`.
- total equals the sum of item quantity multiplied by item price within a one-kopek tolerance.
- a draft contains at most ten items, matching the model proposal limit.
- `DraftSchema` rejects an item whose `productId` is empty.

### 6.8. Cart-write and verified-cart contracts

```ts
interface SetCartProductTarget {
  productId: string;
  quantity: number;
}

interface SetCartProductsInput {
  cartId: string;
  items: SetCartProductTarget[];
  addQuantity: false;
}

interface CartValidation {
  severity: "warning" | "error";
  code: string;
  message: string;
  productId: string | null;
}

interface VerifiedCartItem {
  productId: string;
  quantity: number;
  unitPrice: number;
  available: boolean;
}

interface CheckoutLinks {
  web: string;
  mobile: string;
}

interface VerifiedCart {
  cartId: string;
  status: "verified" | "partially_committed" | "blocked";
  items: VerifiedCartItem[];
  total: number;
  validations: CartValidation[];
  checkoutLinks: CheckoutLinks | null;
}
```

`addQuantity` is the literal `false`, mechanically requiring absolute target quantities. Product targets are unique and positive. Checkout URLs use HTTPS. `checkoutLinks` must be `null` whenever any error-level validation exists or status is not `verified`. A verified cart with checkout links cannot contain an error validation.

These contracts do not authorize a cart write. Persisted approval, idempotency, pre-write refresh, and immediate readback are responsibilities of Tasks 15 and 16.

### 6.9. `SilpoGateway` port

The exported interface is exact:

```ts
export interface SilpoGateway {
  listTools(): Promise<string[]>;
  loadCustomerContext(): Promise<CustomerContext>;
  loadCartContext(): Promise<CartContextResult>;
  updateCartContext(input: UpdateCartContextInput): Promise<CartContext>;
  loadPurchaseHistory(context: CartContext): Promise<RawPurchaseReceipt[]>;
  findProducts(context: CartContext, queries: string[]): Promise<ProductSearchResult[]>;
  getPromotions(context: CartContext): Promise<Promotion[]>;
  getProductDetails(context: CartContext, slug: string): Promise<ProductDetails>;
  getSimilarProducts(context: CartContext, slug: string): Promise<ProductCandidate[]>;
  getTimeSlots(context: CartContext): Promise<TimeSlot[]>;
  setAbsoluteCartQuantities(input: SetCartProductsInput): Promise<void>;
  readCart(cartId: string): Promise<VerifiedCart>;
}
```

The port contains no MCP SDK types and no provider-specific response shapes. `listTools()` exists so live sessions can begin with discovery. Live and demo implementations must later pass the same contract suite.

## 7. Typed application results

`src/lib/result.ts` exports:

```ts
export type Result<T, E> =
  | { ok: true; value: T }
  | { ok: false; error: E };

export type AppErrorCode =
  | "unauthorized"
  | "rate_limited"
  | "needs_slot"
  | "invalid_external_data"
  | "unavailable_product"
  | "cart_validation_error"
  | "partial_commit"
  | "model_invalid_output"
  | "unexpected";

export interface AppError {
  code: AppErrorCode;
  message: string;
  correlationId: string;
  retryAfterMs: number | null;
}
```

The module also exports small constructors `ok(value)` and `err(error)` so callers do not recreate result objects. It contains no logging, HTTP mapping, retry loop, or exception normalization. Error messages are safe summaries and must not carry secret or raw external payload values.

## 8. Server environment contract

### 8.1. Public API

`src/lib/env.ts` has one runtime export, `getServerEnv`, plus the type-only `ServerEnv` export:

```ts
export interface ServerEnv {
  NODE_ENV: "development" | "test" | "production";
  DATABASE_URL: string;
  TOKEN_ENCRYPTION_KEY: string;
  GOOGLE_GENERATIVE_AI_API_KEY: string;
  AGENT_MODEL: string;
  DATA_MODE: "live" | "demo";
  PUBLIC_BASE_URL: string;
}

export function getServerEnv(
  source?: NodeJS.ProcessEnv,
): ServerEnv;
```

The interface may be represented as an inferred type in code, but no additional runtime parser, runtime value, or raw schema is exported.

### 8.2. Validation

- `NODE_ENV` defaults to `development` and accepts only `development`, `test`, or `production`.
- `DATABASE_URL` is non-empty and uses `postgres:` or `postgresql:`.
- `TOKEN_ENCRYPTION_KEY` is non-empty base64 that decodes to exactly 32 bytes.
- `GOOGLE_GENERATIVE_AI_API_KEY` is non-empty.
- `AGENT_MODEL` defaults to exactly `gemini-3.7-flash`.
- `DATA_MODE` defaults to `live` and accepts only `live` or `demo`.
- `PUBLIC_BASE_URL` is an absolute `http:` or `https:` URL; production requires `https:`.
- Unknown environment variables are ignored because the process environment necessarily contains unrelated keys; only the returned object is trusted.
- Validation errors name invalid variable names and constraints but never echo supplied values.
- Requirements do not weaken in test mode. Tests avoid global configuration by calling `getServerEnv` only with explicit synthetic values.

The landing page and module imports must not eagerly call `getServerEnv`, so Task 1 tests and builds do not require local secrets. Server entry points introduced by later tasks call it when they need configuration.

## 9. Error handling and privacy

- Invalid domain input fails at the Zod boundary and is not coerced into guessed shapes.
- Schemas may normalize URL and datetime representation only when the normalization is explicit and tested; they do not probe alternate field names.
- Validation tests use synthetic values. No actual database URL, token, encryption key, API key, address, profile ID, or loyalty identifier is committed.
- Environment errors expose key names only.
- Contract objects sent to Gemini in later tasks must be filtered further according to the agent architecture; the presence of an internal domain field does not authorize model disclosure.
- `SilpoGateway` method signatures do not imply retries. Read retry and write-no-retry policies belong to live adapter tasks.

## 10. Test strategy

### 10.1. Task 1 red-green proof

Focused command:

```bash
pnpm vitest run src/app/page.test.tsx
```

The test is written before the page and fails because the accessible heading is absent. The minimum page implementation makes it pass. The task then runs:

```bash
pnpm test
pnpm lint
pnpm typecheck
pnpm build
```

### 10.2. Task 2 red-green proof

Focused command:

```bash
pnpm vitest run src/features/shared/contracts.test.ts src/lib/env.test.ts
```

Contract tests cover at minimum:

- valid representative purchase, need, product, draft, and verified-cart objects;
- empty draft product ID rejection;
- confidence-band mismatch rejection;
- quantity not aligned with step rejection;
- checkout link rejection for an error validation;
- literal `addQuantity: false` enforcement;
- safe `ok` and `err` construction.

Environment tests cover at minimum:

- all valid synthetic values;
- defaults for `NODE_ENV`, `AGENT_MODEL`, and `DATA_MODE`;
- missing Gemini key rejection;
- missing `PUBLIC_BASE_URL` rejection;
- invalid data mode rejection;
- encryption key decoding to other than 32 bytes rejection;
- non-Postgres database URL rejection;
- non-HTTPS production public URL rejection;
- errors that name a key without echoing its supplied secret value.

Task 2 then runs the focused tests, cumulative `pnpm test`, `pnpm lint`, and `pnpm typecheck`. A production build is rerun because the new shared modules and server-only environment file must remain compatible with the App Router build.

## 11. Implementation sequence and dependency gate

1. Implement and commit Task 1.
2. Confirm all five standard commands exist and the Task 1 focused/static/build checks pass from fresh invocations.
3. Write Task 2 tests against the public contract described here.
4. Implement schemas, types, results, and environment validation without importing later providers.
5. Run focused, cumulative, static, and build verification.
6. Review the Task 2 diff as the shared-contract freeze point and commit it separately.

Task 2 must not begin if Task 1's commands or alias configuration are missing. Tasks 3, 4, and 7 must not begin until Task 2 is integrated.

## 12. Definition of done

The foundation is complete when:

- every file assigned to Tasks 1 and 2 exists and has the single responsibility described here;
- the landing page is accessible and buildable without secrets;
- all shared serializable objects have runtime validation and inferred TypeScript types;
- `SilpoGateway` contains only domain types and matches the normative architecture signature;
- `SetCartProductsInput` requires absolute quantities through `addQuantity: false`;
- checkout links are schema-blocked for non-verified or error-bearing carts;
- environment parsing has one public entry point and validates every architecture-required variable;
- no raw environment object, secret, provider SDK type, or guessed external shape enters the trusted domain;
- Task 1 and Task 2 focused checks, cumulative tests, lint, typecheck, and build pass from fresh invocations;
- the two changes remain independently reviewable and use the documented commit messages.
